===== PAGINA 7 =====

 ¿Qué sale mal?
     Lenguaje confuso: “Pedido” significa distinto en Ventas, Facturación y Logística, pero todos comparten el
     mismo modelo.
     Acoplamiento por datos: un cambio de columna rompe a cuatro equipos (monolito distribuido).
     Transacciones imposibles: “reservar stock + cobrar + despachar” ya no cabe en una sola DB.
     Equipos desalineados: la arquitectura no refleja cómo habla el negocio (ley de Conway).

    Cortar por entidad/tabla optimiza el esquema relacional, no el dominio.




Microservicios (73.40)                                                                                           7

===== PAGINA 8 =====

 Ley de Conway + modelo compartido
     Conway: la estructura del sistema copia la estructura de comunicación de la organización.
     Si el negocio tiene áreas con reglas y vocabularios distintos, forzar un solo modelo “Pedido” global:
         oculta los límites reales,
         concentra el acoplamiento,
         vuelve frágil cualquier “desacople” por red.

 Necesitamos una forma de descubrir límites desde el negocio, no desde las tablas.
 → Domain-Driven Design.

===== PAGINA 9 =====

¿Qué es DDD?

===== PAGINA 10 =====

 Domain-Driven Design
 Enfoque de diseño que prioriza el dominio y su lógica frente a la tecnología.
     Nace para sistemas donde la complejidad del negocio es el problema principal.
     Alinea implementación con el modelo mental del negocio.
     Crea un puente de comunicación entre expertos de dominio y desarrolladores.

 No es un framework ni un stack: es una forma de modelar y acotar software complejo.

Ubiquitous Language

===== PAGINA 14 =====

 Ubiquitous Language
 Lenguaje común y preciso entre desarrolladores y expertos de dominio.
     Se usa en conversaciones, documentación y código.
     Se construye en colaboración; no lo inventan solo los devs.
     Refleja el dominio del problema, no la base de datos ni el framework.

 Si en el código decís OrderDTO y el negocio dice “pedido de reposición”, el lenguaje no es ubicuo.

Domain, Subdomain y
Bounded Context

===== PAGINA 19 =====

 Domain y Subdomains
     Domain: el área de conocimiento del negocio
     (aquí: comercio electrónico / fulfillment).
     No es código: es el mundo de ideas y reglas del
     problema.
     Subdomains: recortes del dominio general
     (ventas, inventario, cobros, envíos, …).

 Core / Supporting / Generic
 No todos los subdominios merecen la misma inversión.

    Tipo                 Rol                                       En nuestro ejemplo

    Core                 Diferencia competitiva; máxima atención   Pricing / reglas de venta (si es el DNA del negocio) o el flujo de
    Domain               al diseño                                 fulfillment propio

                         Necesario, específico del negocio, no
    Supporting                                                     Inventario interno, logística propia
                         diferenciador

    Generic              Resuelto por el mercado; no reinventar    Pagos con tarjeta, email, autenticación


    Microservicios “caros” se justifican más en Core y en Supporting crítico; en Generic preferí SaaS o módulos
    simples.

===== PAGINA 21 =====

 Bounded Context
 Límite explícito dentro del cual un modelo de dominio es válido y consistente.
     Un mismo término puede modelarse distinto fuera del límite.
     Reduce conflictos de modelo y aclara reglas de negocio.
     Cada contexto puede (idealmente) corresponder a un equipo.
     La integración con otros contextos es explícita (APIs, eventos, traducción).




Microservicios (73.40)                                                              21

===== PAGINA 22 =====

 Domain vs Subdomain vs BC
     Subdomain: partición del problema de negocio.
     Bounded Context: partición de la solución (modelo + lenguaje + equipo).
     Idealmente se alinean 1:1, pero no siempre: un subdomain puede implementarse como varios BCs, o un BC
     puede abarcar un supporting + un generic adaptado.

 El diagrama conceptual:

     Domain
     └── Subdomains (Core / Supporting / Generic)
           └── Bounded Contexts ← aquí vive el Ubiquitous Language
                 └── Modelo táctico (Aggregates, Events, …)

===== PAGINA 25 =====

 Customer / Supplier y Conformist
     Customer / Supplier
         El Supplier es upstream (provee capacidades).
         El Customer es downstream (depende de
         ellas).
         Negocian prioridades e interfaces.

     Conformist
         El downstream adopta el modelo del upstream
         tal cual (sin traducción).
         Barato, pero acoplás el lenguaje ajeno.




Microservicios (73.40)                                   25

===== PAGINA 26 =====

 Anticorruption Layer (ACL)
     Capa de adaptación entre dos modelos.
     Traduce el Ubiquitous Language del otro al
     nuestro.
     Protege el Core de modelos ajenos, legacy o de
     terceros.
     En microservicios: a menudo un adapter / gateway
     / anti-corruption service.




Microservicios (73.40)                                  26

===== PAGINA 27 =====

 Open Host Service + Published Language
 Open Host Service (OHS): un contexto expone
 capacidades a muchos consumidores.
     Protocolo e interfaz bien definidos.
     Published Language: el contrato público (JSON
     Schema, eventos, OpenAPI, AsyncAPI…), no el
     modelo interno crudo.
     El host publica un lenguaje de integración; cada
     consumidor puede traducir con ACL si hace falta.

===== PAGINA 28 =====

 Otras relaciones
     Partnership: dos equipos con objetivos
     compartidos y sincronización fuerte.
     Shared Kernel: comparten un subconjunto de
     modelo; ambos lo evolucionan (costoso en
     coordinación).
     Separate Ways: deciden no integrarse aunque
     el negocio se solape; cada uno resuelve por su
     lado.

 Separar caminos ≠ “compartimos la entidad”: es
 aceptar duplicación o caminos paralelos a cambio de
 autonomía.

Del BC al microservicio

===== PAGINA 31 =====

 Bounded Context ≠ microservicio
    Bounded Context                                      Microservicio

    Concepto de diseño/modelo                            Concepto de runtime/despliegue

    Define lenguaje y reglas                             Define proceso, escala, fallos

    Puede ser un módulo en un monólito                   Puede mapear 1 BC    → 1 servicio
 Regla práctica: el BC es el mejor candidato a frontera de servicio.
 No es obligatorio desplegar cada BC por separado el día 1 (monolito modular válido).

===== PAGINA 32 =====

 Señales de un buen límite
     Un equipo puede cambiar el modelo interno sin negociar con todos.
     El Ubiquitous Language es estable dentro y se traduce en el borde.
     Las transacciones fuertes caben dentro del aggregate/contexto.
     La integración exterior tolera latencia y fallos parciales (eventos, sagas).

 Anti-patrones a evitar
     Microservicios por tabla/entidad (ya lo vimos al principio).
                                  → monolito distribuido.
     Shared Database entre servicios
     Shared Kernel demasiado grande → todos se sincronizan para cada change.

DDD táctico (mínimo)

===== PAGINA 35 =====

 Entity
     Objeto con identidad que se mantiene en el tiempo.
     Dos instancias con el mismo id son “la misma cosa” aunque cambien atributos.
     Ejemplos en pedidos:
         Cliente (id de cliente)
         Pedido en Ventas (id de pedido de venta)
         Envío en Logística (id de despacho)

 La igualdad se define por identidad, no por todos los campos.




Microservicios (73.40)                                                              35

===== PAGINA 36 =====

 Value Object
     Se define por sus atributos; no tiene identidad propia.
     Inmutable en la práctica (se reemplaza, no se muta a medias).
     Ejemplos: Dinero (monto + moneda), Dirección, Cantidad, SKU.

  Dinero(100, "ARS") == Dinero(100, "ARS")   ✓
  Pedido#42 == Pedido#42                      ✓ (por id)

                                                           →
 Si dos “direcciones” idénticas son intercambiables Value Object.
                                                                     → reevaluar.
 Si necesitás seguir “esta dirección particular a lo largo del tiempo”




Microservicios (73.40)                                                              36

===== PAGINA 37 =====

 Aggregate
     Cluster de entidades y value objects tratados como una unidad.
     Tiene una raíz (Aggregate Root); el exterior solo habla con ella.
     Frontera de consistencia transaccional: un comando modifica un aggregate a la vez.
     Ejemplo Operaciones: raíz ReservaInventario con líneas de ítems reservados.

     [ReservaInventario] ← raíz
          ├── LineaReserva (ítem, cantidad)
          └── Estado { pendiente | confirmada | liberada }

===== PAGINA 38 =====

 Command y Domain Event
                          Command                                 Domain Event

    Naturaleza            Intención (imperativo)                  Hecho ocurrido (pasado)

    Ejemplo               AprobarPedido                           InventarioReservado

    Fallible              Puede rechazarse                        Ya sucedió; se propaga

    Alcance               Entra a un aggregate/contexto           Sale del contexto hacia otros

 Flujo típico:

  Command → Aggregate aplica reglas → Domain Event(s)

 Los eventos son el puente natural hacia comunicación asíncrona y sagas (próximas clases).

8. EventStorming

===== PAGINA 41 =====

 ¿Qué es EventStorming?
 Técnica de modelado rápida, colaborativa y visual (Alberto Brandolini, ~2013).
     Junta negocio + desarrollo en el mismo muro (o pizarra digital).
     Parte de los Domain Events (pasado perfecto): PedidoCreado, PagoConfirmado.
     Produce alineación y documentación viva del flujo.
     Escala de “big picture” del proceso a diseño de aggregates y BCs.

===== PAGINA 46 =====

 Requisitos — camino feliz
 Cada uno cuenta lo que el sistema debe hacer, desde su punto de vista:
     Gte. Ventas: cuando el usuario presiona comprar, se genera un pedido con los ítems y la cantidad.
     Gte. Operaciones: al recibir un pedido, verifica disponibilidad, lo aprueba y reserva ítems en inventario.
     Gte. Facturación: los pedidos aprobados se facturan y se cobran por tarjeta (el cobro tarda); al
     confirmarse, el pedido queda pagado y pasa a Logística.
     Gte. Logística: los pedidos pagados se programan y despachan; al confirmar recepción, se informa a
     Ventas.

 Paso 3 — Eventos del flujo
