===== PAGINA 19 =====

 OverlayFS: union mount en el host
 OverlayFS no copia los layers: apila directorios del host y expone una vista unificada en un mount point
 nuevo.

    Directorio           Rol en el host

    lowerdir             Layers de la imagen — read-only, compartidos entre containers

    upperdir             Diff writable del container (escrituras y whiteouts)

    workdir              Scratch interno del kernel (mismo filesystem que upperdir)

    merged               Mount point donde el kernel monta el overlay y se ve el resultado


 El proceso del container ve solo merged (su /). En el host siguen existiendo lower/upper/work como dirs
 normales.

===== PAGINA 31 =====

 runc: el que le habla al kernel
  runc exec:
    1. Parsea config.json
    2. Crea namespaces (syscall clone)
    3. Configura cgroups vía systemd
    4. Monta rootfs + proc/sysfs
    5. pivot_root ← chroot seguro
    6. Aplica seccomp + AppArmor/SELinux
    7. Dropea capabilities
    8. exec() → tu proceso

===== PAGINA 33 =====

 Capabilities: root de grano fino
 Históricamente, root = todos los privilegios. Linux los parte en bits independientes: las capabilities.

    Idea                       Detalle

    Qué son                    Privilegios del kernel (CAP_*) que un proceso puede tener o no

    Por qué importan           Un proceso "root" en el container no es root completo del host

    Cómo se controlan          runc dropea; Docker expone --cap-add / --cap-drop

    Default Docker             Conserva 14; dropea el resto (--privileged da todas)


 Ejemplo canónico: CAP_NET_BIND_SERVICE permite bindear el puerto 80 sin ser root absoluto.

===== PAGINA 39 =====

 Resumen
     Containers = namespaces + cgroups + OverlayFS, no un kernel separado
     Capabilities = root partido en bits; Docker conserva 14 y dropea el resto
     El runtime stack es intercambiable porque la OCI estandariza el contrato
     Kernel compartido = la fuente de la eficiencia y también del trade-off de seguridad
