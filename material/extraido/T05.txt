===== PAGINA 11 =====

 Step 1.1 — Concepto: chroot
 chroot cambia la raíz aparente (/) de un proceso: los paths absolutos se resuelven dentro de un árbol que
 armamos a mano.
 No crea namespaces: solo aísla el filesystem. Procesos, red y mounts siguen siendo los del host.

===== PAGINA 17 =====

 Step 1.3 — Concepto: pivot_root
 pivot_root mueve la raíz vieja a .oldroot y la desmonta. Es lo que usa Docker.

                                       chroot                            pivot_root

    Raíz vieja                         accesible                         desmontada

    Mount ns                           no requerido                      sí

    Escape con ..                      posible                           no


 Requisito: la nueva raíz debe ser un mount point (mount --bind sobre sí misma).




Microservicios (73.40)                                                                17

===== PAGINA 18 =====

 Step 1.3 — Comando
  sudo unshare --mount --fork bash
  mount --bind /tmp/container_root_pivot /tmp/container_root_pivot
  cd /tmp/container_root_pivot
  mkdir -p .oldroot
  pivot_root . .oldroot
  cd /
  mount -t proc proc /proc
  umount -l /.oldroot && rmdir /.oldroot
  exec /bin/bash

 Esperado: ls / solo rootfs del container; ls /.oldroot falla.

===== PAGINA 21 =====

 Step 2.1 — Concepto: PID namespace
 El PID namespace numera procesos desde 1.
 Pero /proc del host sigue mostrando todos los PIDs hasta que lo remontás en un mount namespace.
 ⚠️ umount /proc sin --mount afecta al host. No lo hagas en demo en vivo.

 Step 2.1 — PID + mount

  sudo unshare --pid --mount --fork bash
  umount -l /proc 2>/dev/null || true               host pid ns: pid:[4026531836]

                                                   mismo sleep tiene otro PID.

===== PAGINA 23 =====

 Step 2.2 — Qué estamos viendo
     PID ns decide qué procesos existen en la vista
     Mount ns decide qué /proc se lee

     El proceso 1 es el “init” del container: reap de zombies

 Con filesystem + PID tenemos el núcleo de un container. Falta red.

===== PAGINA 25 =====

 Step 3.1 — Concepto: network namespace
 Un net ns aísla interfaces, rutas, iptables y sockets.
 Namespace nuevo         → solo lo (DOWN). Para conectar al host: par veth (cable virtual de dos puntas).
  ip netns add netns1
  ip link add veth0 type veth peer name veth1
  ip link set veth1 netns netns1

===== PAGINA 40 =====

 Step 6.1 — Concepto: cgroup v2
 Jerarquía unificada en /sys/fs/cgroup (cgroup2fs).
 Docker mueve los PIDs del container a un cgroup hoja y escribe límites (memory.max, cpu.max, …).
 Regla hoja: un cgroup con procesos no puede tener subtree_control no vacío.

  cat /sys/fs/cgroup/cgroup.controllers                         controllers=cpuset cpu io memory hugetlb pids …
  mkdir /sys/fs/cgroup/demo_leaf                                sleep 22770 -> 0::/demo_leaf
  echo "+memory +cpu" > /sys/fs/cgroup/cgroup.subtree_control
  sleep 30 & echo $! > /sys/fs/cgroup/demo_leaf/cgroup.procs
  cat /proc/$!/cgroup

===== PAGINA 47 =====

 Step 7.1 — Capabilities
 Root no es todo-o-nada: capabilities granulares (CAP_NET_BIND_SERVICE, …).

  capsh --print
  capsh --drop=cap_net_bind_service -- -c '
    python3 -c "import socket; s=socket.socket(); s.bind((\"\", 80))"
  '

  → Permission denied

 setcap solo afecta binarios ELF, no scripts Python/Bash.
 Docker mantiene ~14 capabilities y dropea el resto.

===== PAGINA 48 =====

 Step 7.2 — Seccomp
 Filtra syscalls. Modo estricto: solo read/write/exit/sigreturn.

  # programa C: prctl(PR_SET_SECCOMP, SECCOMP_MODE_STRICT); fork();
  # → proceso muere al intentar fork

 Docker aplica un perfil BPF por defecto. Defensa en profundidad junto a namespaces y capabilities.
