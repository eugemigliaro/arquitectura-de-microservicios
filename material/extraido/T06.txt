===== PAGINA 7 =====

 Imagen de un contenedor
     Archivo tar.gz que contiene la información
     necesaria para crear un contenedor.
     Incluye los valores de configuración (metadata) y
     los archivos necesarios (en layers).

 Los layers se reutilizan entre imágenes: dos apps
 sobre la misma base comparten los mismos layers en
 disco y en la red.

===== PAGINA 9 =====

 Desde cero: un binario estático
 Arrancamos con lo mínimo: un binario compilado estáticamente.

  // hw.go                                             # Dockerfile
  package main                                         FROM scratch
                                                       COPY hw /
  import "fmt"                                         ENTRYPOINT ["/hw"]

  func main() {                                        docker build -t hw .
      fmt.Println("hello world")                       docker run hw
  }

  docker run --rm -v "$PWD":/usr/src/myapp \
    -w /usr/src/myapp golang go build -v hw.go

 FROM scratch es la imagen vacía: 0 bytes. La imagen consiste exclusivamente en nuestro binario.

===== PAGINA 13 =====

 FROM · COPY · RUN
  FROM <image>

 Imagen base sobre la que se construye. scratch = desde cero. Instrucción obligatoria.

  COPY <src>... <dest>

 Incorpora archivos del build context a la imagen.

  RUN <command>

 Ejecuta un comando en tiempo de build, sobre el contexto construido hasta ese momento. Todo lo que el
 comando necesite ya tiene que existir en la imagen.

  FROM python:3
  COPY requirements.txt ./
  RUN pip install --no-cache-dir -r requirements.txt
  COPY . .




                                                              Fuente: https://docs.docker.com/develop/develop-images/instructions/

===== PAGINA 14 =====

 ENTRYPOINT y CMD
  ENTRYPOINT ["executable", "arg1"]   # el ejecutable fijo
  CMD ["param1", "param2"]            # los argumentos por defecto

  docker run [OPTIONS] IMAGE [COMMAND] [ARG...]

 Lo que se pasa después de la imagen reemplaza al CMD y se aplica sobre el ENTRYPOINT.

  FROM ubuntu
  COPY args /
  ENTRYPOINT ["/args", "first"]
  CMD ["second"]


                                                  /args first second
                                                     ENTRYPOINT      CMD (DEFAULT)




   # docker run args                                                  # docker run args third
   first second                                                       first third

===== PAGINA 16 =====

 ARG y ENV
  ARG <name>[=<default>]

 Parámetro exclusivo del build.

  docker build --build-arg="NAME=value" .

  ENV <key>=<value>

 Variable de entorno: disponible en los RUN
 posteriores y en el container en ejecución.
 Se combinan para parametrizar el build:

  ARG A_VARIABLE
  ENV an_env_var=$A_VARIABLE

===== PAGINA 17 =====

 USER y WORKDIR
  WORKDIR /path/to/workdir

 Cambia el directorio de trabajo para el resto del build y para la ejecución.

  USER <user>[:<group>]

 Define el usuario para los RUN, ENTRYPOINT y CMD siguientes.
 Por defecto, un container corre como root. Eso significa uid 0 dentro y fuera del namespace si no hay
 user namespace remapping.

  FROM node:20-slim
  WORKDIR /app
  COPY --chown=node:node . .
  USER node
  CMD ["node", "index.js"]

===== PAGINA 18 =====

 Metadata de la imagen
  EXPOSE 8000

 Documenta qué puerto usa la app. No publica nada: no reemplaza al -p de docker run ni al ports: de
 Compose. Habilita docker run -P.

  LABEL maintainer="catedra-microservicios@itba.edu.ar"
  LABEL org.opencontainers.image.source="https://gitlab.com/..."

 Metadata arbitraria, legible con docker image inspect. Las claves org.opencontainers.image.* son
 estándar OCI.

  HEALTHCHECK --interval=10s --timeout=3s --retries=3 \
      CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/ping')" || exit 1

 Chequeo intrínseco a la imagen. El equivalente en Compose lo vemos en la segunda parte.

 El build context

===== PAGINA 27 =====

 Multi-stage builds
  FROM golang:1.24 AS builder
  WORKDIR /src
  COPY . .
  RUN go build -o /bin/app .

  FROM gcr.io/distroless/static-debian12
  COPY --from=builder /bin/app /app
  ENTRYPOINT ["/app"]

 El build stage tiene compiladores y deps de desarrollo; el runtime stage solo lleva lo que copiás
 explícitamente. Típicamente ~20 MB vs ~1 GB con el toolchain.

===== PAGINA 28 =====

 Multi-stage: Go a scratch
  FROM golang:1.24 AS builder
  WORKDIR /workspace
  COPY go.mod go.sum ./
  RUN --mount=type=cache,target=/root/.cache/go-build \
      go mod download
  COPY . .
  RUN --mount=type=cache,target=/root/.cache/go-build \
      CGO_ENABLED=0 go build -o manager ./cmd/main.go

  FROM scratch
  COPY --from=builder /workspace/manager .
  ENTRYPOINT ["/manager"]

 CGO_ENABLED=0 fuerza el linkeo estático        → no hace falta ningún intérprete en runtime.

===== PAGINA 31 =====

 Cómo leer ese scan (y dos trampas)
 1. El número crudo miente. De las 3028 de python:3.13, 316 son de linux-libc-dev: headers del
 kernel. Un container no ejecuta su propio kernel — usa el del host. Nunca se van a explotar desde ahí.
 → El número accionable es la columna con fix: 514, no 3028.
 2. "Distroless" no quiere decir "actualizado". distroless/python3-debian12:latest empaqueta
 Python 3.11.2, y ahí están 18 de sus CVEs con fix. Termina peor que python:3.13-slim, que es el doble
 de grande pero está al día.
 Distroless reduce la superficie. Mantener la base al día es un problema aparte, y sigue siendo tuyo.

===== PAGINA 36 =====

 Lo definitivo: deploy por digest
  # Manifiesto de Kubernetes
  image: ghcr.io/org/app@sha256:abc123def456...
  # En vez de: image: ghcr.io/org/app:v1.2.3

 El digest SHA256 se computa a partir del contenido del manifiesto: es criptográficamente inmutable.
 Complemento: los registries (ECR, ACR, Artifact Registry) permiten políticas de inmutabilidad que
 rechazan sobrescribir un tag ya publicado.

===== PAGINA 37 =====

 Errores más comunes
     Olvidarse del .dockerignore     → archivos con secrets dentro de la imagen
     COPY . . antes del install   → el cache nunca pega
     Correr como root  → sin necesidad, y por default
     Secrets en ARG/ENV → quedan en el historial de layers
     Usar el tag latest → drift silencioso de versiones
     Alpine para Python/Node → instalaciones de 4 min + bugs de DNS

===== PAGINA 40 =====

 Resumen
     Una imagen = layers + metadata; la base se elige por el userspace que tu binario necesita
     Builds rápidos = ordenar de lo menos volátil a lo más volátil + BuildKit
     Imágenes seguras = multi-stage + distroless + .dockerignore + no-root
     Trazabilidad = tags inmutables + deploy por digest
