===== PAGINA 4 =====

 docker compose
 Permite construir aplicaciones utilizando un archivo YAML para indicar las acciones de:
     ejecutar uno o más contenedores
     definir la cantidad de instancias para cada contenedor
     crear y usar volúmenes
     crear y usar redes
     definir variables de ambiente
     definir qué pasa si un contenedor falla
     definir dependencia entre contenedores

 docker compose implementa, de una forma más simple, el concepto de orquestación de contenedores.

===== PAGINA 13 =====

 docker compose watch
 Actualiza servicios automáticamente al guardar cambios. Sólo funciona con servicios que usan build.

  services:
    web:
      build: .
      command: npm start
      develop:
        watch:
          - action: sync
            path: ./web
            target: /src/web
            ignore:
              - node_modules/
          - action: rebuild
            path: package.json

 Acciones: sync (copia archivos), rebuild (reconstruye la imagen), sync+restart.

 Estados del healthcheck
 Un comando que Docker ejecuta periódicamente dentro del contenedor para comprobar si está "sano".
                                  exit ≠ 0

           starting
                                             exit ≠ 0   unhealthy
                         exit 0   healthy
                                             exit 0


 Exit code de la prueba: 0 = healthy · cualquier otro = unhealthy.
 No reinicia contenedores automáticamente; solo informa del estado.

 Readiness vs liveness
 Readiness — ¿puede aceptar trabajo?                      Liveness — ¿sigue vivo, o hay que matarlo?
 Si falla, los dependientes no deberían usarlo todavía.   Si falla, el workload está roto y la plataforma debe
 En Compose, service_healthy los mantiene                 reiniciarlo.
 esperando.                                               El healthcheck de Compose está más cerca de
                                                          readiness: no reinicia el container cuando los checks
                                                          fallan.

===== PAGINA 19 =====

 ¿Dónde se define el healthcheck?
 Dos lugares posibles: en el Dockerfile (HEALTHCHECK ...) o en el docker-compose.yml
 (healthcheck:). Si el chequeo es intrínseco a la imagen, va en el Dockerfile; si depende del entorno, en
 Compose.
 El campo test admite ["CMD", "exe", "arg"] (exec directo) y ["CMD-SHELL", "comando"] (pasa por
 sh -c).

  # HTTP                                                          # Redis
  ["CMD-SHELL", "curl -fsS http://localhost:8080/health || exit   ["CMD", "redis-cli", "ping"]

  # Postgres                                                      # Mongo
  ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER:-postgres}"]      ["CMD-SHELL", "mongosh --quiet --eval 'db.runCommand({ping:1})

 Buenas prácticas: comandos rápidos y locales · start_period acorde al warm-up · sin red externa · las
 dependencias del test (curl, pg_isready) tienen que estar en la imagen.

===== PAGINA 22 =====

 El servicio de base de datos
  services:
    db:
      image: mariadb:10-focal
      command: '--default-authentication-plugin=mysql_native_password'
      restart: always
      healthcheck:
        test:
          - 'CMD-SHELL'
          - 'mysqladmin ping -h 127.0.0.1 --password="$$(cat /run/secrets/db-password)" --silent'
        interval: 3s
        retries: 5
        start_period: 30s
      secrets:
        - db-password
      volumes:
        - db-data:/var/lib/mysql
      environment:
        - MYSQL_DATABASE=example
        - MYSQL_ROOT_PASSWORD_FILE=/run/secrets/db-password
      expose:
        - 3306

 Más abajo, las declaraciones globales: volumes: db-data: y secrets: db-password: {file:
 db/password.txt}.
