===== PAGINA 4 =====

 ¿Cómo hablan los microservicios?
     En un monolito, la comunicación se realiza a
     través de llamadas a funciones internas en
     memoria.
     En microservicios, la comunicación es mediante
     la red.
     Comunicación por red = latencia, fallos y
     particiones temporales.
     Elegir el patrón correcto de comunicación en
     microservicios es clave.

 Dos grandes familias
     Síncrono = enviás un request y esperás la
     respuesta.
     Asíncrono = “disparás y seguís”; la respuesta (si
     existe) llega luego.

 Ninguno es mejor que el otro, depende.
 Hoy vemos síncrono en profundidad. Asíncrono y
 los patrones de coordinación vienen en las próximas
 dos clases.

===== PAGINA 9 =====

 REST: Buenas Prácticas
     Versionado desde el día uno: /api/v1/ en la URL o header Accept-Version.
     Paginación siempre: cursor-based > offset (offset se rompe con inserciones concurrentes).
     Idempotencia en mutaciones: header Idempotency-Key (patrón Stripe).
     HTTP status codes correctos: 201, 404, 409 — no todo es 200 OK con error en el body.
     HATEOAS selectivo: links a acciones posibles en el response.
     Rate limiting + circuit breaker en APIs públicas.

===== PAGINA 10 =====

 REST: Anti Patterns Comunes
     “200 OK” con error en el body: { "status": 200, "error": "Not Found" }; imposible cachear,
     imposible filtrar en load balancers.
     Verbos en la URL: POST /createOrder en vez de POST /orders; REST son recursos, no funciones.
     Chatty APIs: 10 calls para armar una pantalla   → considerar BFF o GraphQL.
     Ignorar ETag / If-None-Match: sin conditional requests, el cache no sirve.
     No documentar errores: el 400 sin body no le dice al consumidor qué corregir.

===== PAGINA 12 =====

 gRPC: Buenas Prácticas
     Repo único de .protos: un solo repositorio, versionado con tags; CI genera clientes.
     Retrocompatibilidad: nunca borrar ni renumerar campos; reserved para campos retirados.
     Deadlines siempre: timeout explícito en todo call; un servicio lento no traba al caller.
     Enums con UNKNOWN = 0: el default de protobuf es 0; sin UNKNOWN no sabés si es intencional.
     Streaming solo cuando hace falta: unary es más simple de operar y debuggear.
     Metadata para tracing: propagar traceId en headers gRPC, no en el payload.




Microservicios (73.40)                                                                             12

===== PAGINA 13 =====

 gRPC: Anti Patterns comunes
     Olvidar deadlines: sin timeout, un servicio lento propaga el hang a toda la cadena (cascading failure).
     Proto files copiados entre repos: divergencia inevitable; un equipo actualiza, otro no.
     Payloads enormes en unary: gRPC tiene límite default de 4 MB; streaming existe por algo.
     Ignorar reserved: borrar un campo y reusar el número    → deserialización corrupta silenciosa.
     gRPC para todo: para APIs públicas o integraciones externas, REST sigue siendo mejor.

===== PAGINA 15 =====

 GraphQL: Buenas Prácticas
     DataLoader para N+1: sin DataLoader, 10 órdenes con productos = 1 + 10 queries a la DB.
     Limitar profundidad: max depth (ej.: 5 niveles) para evitar queries que derriten el server.
     Complejidad estimada: asignar “costo” a cada campo, rechazar queries que excedan el límite.
     Persisted queries en producción: el frontend envía un hash, no la query completa.
     Resolvers delgados: el resolver orquesta, la lógica en services/repositories.
     Schema-first: definir el schema SDL como contrato, generar código desde ahí.




Microservicios (73.40)                                                                             15

===== PAGINA 16 =====

 GraphQL: Anti-patterns y cuándo NO usarlo
     GraphQL para CRUD simple: si tu API es GET /users/:id, REST es más simple y cacheable.
     GraphQL service-to-service: para comunicación interna entre microservicios, gRPC gana en
     performance.
     Schema gigante sin Federation: un solo server con 500 types es inmantenible; usar Apollo Federation o
     schema stitching.
     Resolver que hace lógica de negocio: el resolver es un controller, no un service; debe ser delgado.
     No limitar queries: sin depth limit + complexity limit, { user { friends { friends { friends...
     } } } } puede tirar el server.
     Subscriptions para todo: websockets son pesados de operar; considerar SSE o polling para datos que
     cambian poco.

 ConnectRPC: gRPC sin las partes molestas
 Problema: gRPC no funciona en browsers y no se
 puede testear con curl.
 Mismo .proto, un server, 3 protocolos:
                    →
     Connect HTTP/1.1 + JSON (curl, Postman,
     browsers).
               →
     gRPC HTTP/2 + Protobuf binario (service-to-
     service).
     gRPC-Web            → HTTP/1.1 + Protobuf (browsers, sin
     proxy).

 SDK en varios lenguajes: Go, TS, Python, Kotlin, Swift,
 Dart.

===== PAGINA 22 =====

 Dos letras, y toda la demo sale de ahí
     λ (lambda) — lo que llega: requests por segundo.
     μ (mu) — lo que el sistema puede terminar: requests por segundo.

 Si λ es menor que μ, la espera es transitoria. Si λ supera a μ, el trabajo se acumula y algo se tiene que
 romper: o esperás, o perdés.
 La pregunta de toda la demo es qué se rompe, y quién paga.

===== PAGINA 23 =====

 El experimento
    20 clientes              cada uno con 5 cosas que hacer, una tras otra

    Closed-loop              no manda la siguiente hasta que vuelve la anterior

    2 workers                3 requests en ejecución cada uno

    Capacidad                cpus: 0.5 por worker     → μ ≈ 4 req/s
    Fallas                   20%, y ocurren después de hacer el trabajo

    Paciencia                timeout de 3 s, y ahí pasa a la siguiente


 Con 3 s de paciencia, 20 clientes demandan ≈ 6,7 req/s. El sistema da 4.

===== PAGINA 26 =====

 Lo que le agregamos al sync
 Bulkhead — 3 en ejecución más una sala de espera de 2. El sexto se va con 503 al instante, sin tocar la CPU.
 Retry — hasta 3 reintentos, con backoff exponencial y jitter: 100 ms, 200 ms, 400 ms, cada uno con ruido.
 Ningún patrón nuevo y la misma capacidad. Cambia a quién dejamos entrar y cuánto insiste el que
 quedó afuera.

===== PAGINA 30 =====

 Misma capacidad, distinto destino del trabajo
 Las cuatro corridas son el mismo binario, con el mismo trabajo, bajo el mismo medio core. μ es idéntica
 por construcción.
 Lo único que cambia es qué le pasa a lo que no entra:
     Naive lo pierde, y encima quema CPU en pedidos que ya nadie espera.
     Bulkhead lo rechaza rápido y barato: protege al servicio.
     Retry lo recupera, si el rechazo es barato: 41 a tiempo.
     La cola no lo pierde nunca, pero lo entrega tarde: 4 a tiempo.

 La cola no agrega capacidad. Convierte pérdida en latencia.

===== PAGINA 32 =====

 ¿Y cuando el pedido falla?
 El 20% falla después de hacer el trabajo. Alguien tiene que decidir qué hacer con él.
     Reintentar — con backoff exponencial y jitter
     Idempotencia — el trabajo ya se hizo una vez
     DLQ — tras N intentos, apartar en vez de perder
     Circuit breaker — si falla siempre, dejar de intentar

 Sync lo decide el cliente, con el reloj. La cola lo decide el broker, con intentos.

===== PAGINA 33 =====

 Lo que esta demo NO prueba
     La cola era en memoria: si el broker se muere, se pierde todo el backlog.
     Te salvó de la sobrecarga, no de un crash.
     El broker puede entregar el mismo mensaje dos veces.
     Con λ > μ sostenida, ninguna cola alcanza: el backlog llega al techo y el rechazo vuelve.

 Persistencia, garantías de entrega e idempotencia: clase 7.

===== PAGINA 34 =====

 Multi-protocolo: La arquitectura ganadora
     REST→ APIs públicas, externas.
     gRPC/ConnectRPC → interno, baja latencia.
     Message Queue → eventos, procesamiento async.
     GraphQL → BFF, frontends con datos complejos.

 No existe un protocolo maestro. La arquitectura óptima combina opciones según el problema a resolver.

===== PAGINA 36 =====

 Recap: ¿Qué nos llevamos?
     Síncrono vs asíncrono: no hay mejor, hay trade-offs.
     REST público, gRPC interno, GraphQL para BFF.
     El contrato es lo que importa: OpenAPI, .proto, schema SDL.
     Deadlines, versionado e idempotencia no son opcionales.
     ConnectRPC ataca una fricción concreta, no reemplaza a gRPC.
     Bajo sobrecarga: sync pierde trabajo, la cola acumula latencia.
     Multi-protocolo: combinás según el caso de uso.

 Lo que viene: asíncrono y EDA (clase 7) y estado distribuido y Saga (clase 8).
