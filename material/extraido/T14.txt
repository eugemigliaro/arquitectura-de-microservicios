===== PAGINA 8 =====

 ¿Cuándo NO usar async?
     Necesitás la respuesta ya, para decidir el siguiente paso.
     El flujo es simple y un único consumidor alcanza.
     No podés pagar el costo operativo de un broker (equipo, monitoreo, on-call).
     La consistencia inmediata importa más que el desacople.

 Async no es progreso automático — es un trade-off. Se paga con complejidad operativa lo que se gana
 en resiliencia y escala.

Event-Driven Architecture

===== PAGINA 15 =====

 Event-Driven Architecture (EDA)
     Sistemas reactivos: los servicios emiten eventos describiendo hechos ocurridos. Otros servicios
     reaccionan.
     Desacoplamiento: el emisor no sabe, ni le interesa, quién está escuchando.

 Distinción importante:
                                       → pasado, inmutable, sin expectativa.
     Eventos: "algo pasó" (OrderCreated)
     Comandos: "hacé algo" (ProcessPayment) → imperativo, espera resultado.

===== PAGINA 17 =====

 Tres formas de llevar información en un evento
     Event notification: "algo pasó", payload mínimo (OrderCreated { orderId }). El que escucha, si
     necesita más, pregunta.
     Event-carried state transfer: el evento lleva el estado completo (OrderCreated { orderId, items,
     total, customer }). Nadie necesita volver a preguntar.
     Comando: no es un evento — es una instrucción dirigida con expectativa de resultado (ChargePayment).

 Trade-off: notification es liviano pero genera llamadas de vuelta; state transfer es autosuficiente pero duplica
 datos entre servicios.




Microservicios (73.40)                                                                                              17

===== PAGINA 18 =====

 Claim check: cuando el payload no cabe en el bus
 State transfer sin límites termina en eventos gigantes (imágenes, PDFs, PII pesada).
     El evento lleva un puntero (uri, blobId) al payload completo en un store (S3, DB, object storage).
     Quien necesita el detalle lo descarga; el resto solo reacciona al hecho.
     El bus transporta el hecho, no el archivo.

 Complementa notification vs state transfer: no es todo-o-nada — podés llevar metadata rica y dejar el blob
 afuera.

===== PAGINA 19 =====

 CQRS light: un write, muchos reads
     Command Query Responsibility Segregation: el modelo que escribe no tiene por qué ser el que se
     consulta.
     El servicio de escritura emite eventos; uno o más read models (projections) los consumen y materializan
     vistas optimizadas para lectura.
     Kafka encaja natural: el mismo log alimenta facturación, analytics y una proyección de "mis órdenes" sin
     acoplar al writer.

 No es Event Sourcing completo (el historial como única fuente de verdad). Es separar write path de read path
 — y el bus es el puente.

===== PAGINA 26 =====

 Durabilidad: lo que un motor de orquestación agrega
     El estado del workflow se persiste en cada paso, no solo vive en memoria.
     Si el worker que ejecuta OrderSaga se cae justo después de reserveInventory, al reiniciar retoma
     exactamente ahí — no se pierde la compensación, no se cobra dos veces.
     Esta durabilidad es la razón de ser de Cadence/Temporal: no es "un scheduler más", es lo que hace
     confiable ejecutar una Saga larga sin reinventar checkpoints a mano.

 Conecta con la sección 6: esto es la misma preocupación que resuelve el outbox pattern, pero aplicada al
 orquestador en vez de a un único servicio.

===== PAGINA 27 =====

 Timeouts y deadlines en la Saga
 Una Saga sin deadline puede quedar colgada para siempre: pago que no responde, repartidor que nunca
 acepta.
     Cada paso (y la Saga entera) tiene un timeout explícito.
     Al vencer: rama de compensación (liberar stock, cancelar orden) — igual que un PaymentFailed.
     En Temporal/Cadence: timers durables; sobreviven al restart del worker.

 Sin timeout, "compensación" es teoría: en la práctica el flujo se pudre en un estado intermedio.

===== PAGINA 29 =====

Cómo funciona Kafka

===== PAGINA 30 =====

 ¿Por qué existe Kafka?
     Los sistemas modernos necesitan intercambiar datos continuamente.
     Las integraciones punto a punto generan alto acoplamiento.
     Productores y consumidores no siempre trabajan al mismo ritmo.
     Muchas aplicaciones necesitan reaccionar en tiempo real y conservar el historial para reprocesar.


  Kafka aparece cuando integrar sistemas a gran escala empieza a ser un problema en sí mismo.

===== PAGINA 31 =====

 La idea central: el log
     Un log es una secuencia ordenada de registros inmutables.
     Se escribe solo al final (append-only).
     Responde dos preguntas: ¿qué pasó? y ¿en qué orden?
     Leer no elimina el dato — distintos consumidores pueden leer el mismo historial, cada uno a su propio
     ritmo.


                         Consumir no es sacar un mensaje: es avanzar una posición de lectura.

===== PAGINA 32 =====

 Topics y particiones
     Un topic agrupa eventos del mismo tipo (order-created, payment-approved).
     Un topic no es una cola: los eventos permanecen según la política de retención, y cada consumidor lleva
     su propio offset.
     Un topic se divide en particiones para paralelizar.
     Kafka garantiza orden dentro de una partición — no entre particiones de un mismo topic.




Microservicios (73.40)                                                                                         32

===== PAGINA 33 =====

 La key decide la partición
     partición = hash(key) % cantidad_de_particiones
     Misma key           → misma partición → orden relativo preservado para esa entidad.
     Ejemplos típicos de key: orderId, customerId, accountId.
     Sin key (o key distinta cada vez), Kafka reparte round-robin — sin garantía de orden entre esos eventos.

===== PAGINA 35 =====

 Anti-pattern: key ausente o mal elegida
 Después de la demo: el bug de ordenamiento casi nunca es "Kafka se rompió".
     Sin key: round-robin   → eventos de la misma orden en particiones distintas → el consumer puede ver Paid
     antes que Created.
     Key inestable (uuid() por mensaje, o un campo que cambia): misma entidad salta de partición.
     Key demasiado gruesa (todo con tenantId): una partición caliente, el resto ocioso.

 Regla: la key es parte del contrato de orden. Elegila por la entidad cuyo orden relativo importa (orderId,
 no "lo que haya a mano").

 Brokers y replicación
     Un cluster Kafka está formado por varios brokers.
                                                         Broker 1 — P0 (líder), P1 (réplica)
     Las particiones se distribuyen entre brokers — el
     topic es lógico, el broker es físico.
                                                         Broker 2 — P1 (líder), P2 (réplica)
     Cada partición puede tener varias réplicas: una
     líder, el resto sigue.                              Broker 3 — P2 (líder), P0 (réplica)
     Si un broker cae, otra réplica asume como líder —
     así Kafka tolera fallos sin perder datos.

===== PAGINA 37 =====

 Producers y Consumers
     El producer escribe records en un topic; con o sin key.
     El consumer lee con modelo pull — decide hasta dónde avanzó, y puede reiniciarse y continuar donde
     dejó.
     Los consumers se agrupan en consumer groups para repartirse el trabajo.
     Ninguno de los dos necesita conocer al otro — solo el topic.

===== PAGINA 38 =====

 Offsets: leer no es sacar
     Cada consumer lleva su propio offset (próxima posición a leer), guardado aparte del log.
     El log no cambia cuando se lee — dos consumers pueden estar en offsets distintos del mismo topic.
     Por eso Kafka permite replay: volver el offset a 0 sin perder ni duplicar el historial.

 Consumer Groups: paralelismo real
     Dentro de un mismo consumer group, una partición se asigna a un solo consumer a la vez.
     Paralelismo máximo = cantidad de particiones. Un quinto consumer con 4 particiones queda ocioso.
     Si un consumer cae, el grupo rebalancea: sus particiones se redistribuyen entre los que quedan.

===== PAGINA 43 =====

 Consumer lag: el termómetro del async
 La demo de clase 6 ya lo midió: la cola no pierde requests, pero la latencia se fue a 30 s. Eso es lag.
     Lag = diferencia entre el final del log y el offset del consumer.
     Es la métrica operativa #1: no "¿el broker está up?", sino "¿estamos al día?".
     Respuestas típicas: más consumers (hasta #particiones), más particiones, optimizar el handler, o aceptar
     latencia bajo pico.

 Kafka no es un buffer infinito e invisible: el lag es la factura del desacoplamiento temporal.

===== PAGINA 45 =====

Patrones de confiabilidad

===== PAGINA 46 =====

 El problema: escribir en la DB y publicar el evento
 Un servicio típico hace dos cosas al procesar una orden:
 1. Actualiza su base de datos.
 2. Publica un evento contándolo.

 ¿Qué pasa si el proceso se cae entre el paso 1 y el paso 2? La orden quedó guardada, pero nadie se
 enteró. O al revés: el evento salió, pero el commit falló.
 Esto se conoce como el problema del dual write — dos sistemas distintos (DB y broker) que no comparten
 transacción.
 Anti-pattern: publicar "a mano" después del commit (o antes) y esperar que no falle nunca. El patrón
 correcto es Outbox (o CDC).

 La idea: no publicar el evento, guardarlo. El evento pasa a ser una fila más en la misma DB que el cambio
 de negocio.

 Consumidor idempotente: el contrato
 Kafka (y casi todo broker) entrega at-least-once en la práctica. Los reintentos van a pasar.
     Usá el id de CloudEvents (o una business key estable) como clave de dedupe.
     El efecto de negocio debe ser seguro ante repetición: Inbox, upsert, o "ya procesado   → ACK".
     Anti-pattern: "Kafka me da exactly-once, no necesito idempotencia." Falso consuelo — EOS de Kafka no
     reemplaza el diseño del handler.

 La clase 7 cubre la mecánica con Valkey; esta slide fija la regla para el TP.

===== PAGINA 52 =====

 Retries, DLQ y poison messages
     Reintentos con backoff: un fallo transitorio (timeout, servicio caído un segundo) se reintenta, espaciando
     los intentos.
     Dead-letter queue (DLQ): mensajes que fallaron N veces se mueven aparte — así no bloquean al resto.
     Poison message: payload corrupto o bug de deserialización. Reintentarlo para siempre no lo arregla — a
     la DLQ para revisión manual.

===== PAGINA 53 =====

 Anti-pattern: reintentar para siempre
 En una cola clásica, un poison message + retry infinito bloquea a los que vienen detrás.
 En Kafka es peor de lo que parece: un consumer que no avanza el offset en una partición deja toda esa
 partición atrasada (lag crece solo ahí). Los demás consumers del grupo siguen, pero esa key/entidad se
 pudre.
 Regla: tope de intentos   → DLQ (u otro topic) → alerta humana. Sin DLQ no hay resiliencia, hay denegación de
 servicio accidental.

 Correlación: trazar la cadena async
 Anti-pattern "async sin observabilidad" se arregla en el contrato del evento, no solo con un APM:
     correlationId: identifica el flujo de negocio entero (ej. orderId / id de Saga). Todos los eventos del
     mismo pedido lo comparten.
                                                                                 →
     causationId: id del evento (o request) que causó este. Arma el árbol padre hijo.
     Viajan como extensiones CloudEvents; OpenTelemetry los retoma en la clase de Observabilidad.

 Sin esto, debuggear la compensación de 3 saltos de la sección 4 es arqueología en 3 logs distintos.

===== PAGINA 55 =====

 Evolución de esquema en eventos
 Los consumidores no se despliegan al mismo tiempo que el productor. El contrato tiene que tolerarlo.
     Versioná el type (com.itba.order.created.v2) o usá compatibilidad hacia atrás en el payload.
     Additive changes (campos nuevos opcionales) ≫ renombrar/borrar campos.
     Un breaking change mal anunciado se convierte en poison message en cascada.

 AsyncAPI + CloudEvents en el lab no son burocracia: son el contrato que evita ese silent break.

===== PAGINA 58 =====

 Checklist de decisión
     ¿Necesitás la respuesta ya, para seguir?  → síncrono.
     ¿Un evento, múltiples reacciones independientes? → pub/sub / EDA / fan-out (distintos consumer groups).
     ¿Necesitás replay o que varios consumidores lean el mismo historial? → Kafka.
     ¿Mensajería simple y liviana, sin gran volumen? → NATS.
     ¿Separar write path de lecturas optimizadas? → CQRS light sobre el mismo log.
     ¿Payload pesado o PII? → claim check, no fat event.
     ¿Una transacción de negocio cruza varios servicios? → Saga + timeouts.
       Pocos pasos, equipos autónomos → coreografía.
       Muchos pasos, necesitás visibilidad end-to-end → orquestación (Temporal, Camunda, Step Functions).

     ¿Dual write DB↔broker? → Outbox (+ CDC o poller) / Inbox en el consumidor.

===== PAGINA 59 =====

 Anti-patterns (1/2)
     Monolito distribuido vía eventos: todos escuchan todo, nadie entiende el flujo — coreografía sin
     límites.
     God topic: un solo topic events para todo el sistema   → acoplamiento + consumidores ruidosos. Preferí
     topics/tipos acotados (type CloudEvents claro).
     Chatty / ping-pong events: A emite    → B emite → A reacciona… RPC disfrazado de EDA.
     Sync-over-async: pedir respuesta inmediata sobre el canal async (o polling infernal / request-reply para
     todo).
     Acoplamiento temporal disfrazado: "es async" pero el flujo no avanza si el otro servicio no responde ya
     — faltaba un timeout o un modelo sync honesto.
     Async sin observabilidad: sin correlationId / causationId / traces, la cadena de 5 servicios es
     opaca.

===== PAGINA 60 =====

 Anti-patterns (2/2)
     Dual write sin Outbox: commit + publish "a mano" — el proceso se cae en el medio y el mundo queda
     inconsistente.
     Asumir exactly-once: saltarse Inbox/idempotencia porque "Kafka lo garantiza".
     Key ausente o inestable: orden roto entre eventos de la misma entidad; o partición caliente.
     Retry forever / sin DLQ: poison message frena la partición (o la cola) para todos.
     Fat events / PII en el bus: payloads enormes o datos sensibles viajando a N consumidores — usá claim
     check y minimizá el payload.
     Ignorar consumer lag: el broker "está verde" mientras el SLA de frescura ya explotó (o el disco se llena).
     Orquestador-monolito: un workflow que conoce 20 internos de cada servicio — acoplamiento central
     peor que la coreografía que reemplazó.
     Happy-path async + compensación sync sin deadline: liberar stock con un DELETE síncrono "cuando
     se pueda", sin timeout de Saga.
