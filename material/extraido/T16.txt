===== PAGINA 5 =====

 ¿Qué hace Kubernetes?
 Kubernetes automatiza las tareas operativas de la administración de contenedores: despliega aplicaciones,
 coordina sus actualizaciones y mantiene la cantidad deseada de réplicas.
 También permite configurar escalado automático y comprobar el estado de las aplicaciones. Las métricas, el
 almacenamiento de logs y otras funciones requieren componentes adicionales.

===== PAGINA 13 =====

 Contenedores en Linux
 Un contenedor ejecuta procesos sobre el kernel del nodo.
     Los namespaces de Linux aíslan vistas del sistema: procesos, red y montajes, entre otras.
     Los cgroups controlan el uso de recursos, como CPU y memoria.
     El filesystem raíz proviene de la imagen, con una capa escribible propia.

 Estos mecanismos son complementarios: aislamiento y control de recursos.
 Los namespaces del kernel no son los objetos Namespace de la API de Kubernetes.

===== PAGINA 19 =====

 Fases del Pod
     Pending: aceptado; espera asignación o preparación de contenedores, incluida la descarga de imágenes.
     Running: asignado a un nodo; contenedores creados y al menos uno ejecutándose, iniciándose o reiniciándose.
     Succeeded: todos finalizaron con éxito y no se reiniciarán.
     Failed: todos terminaron; alguno falló y no se reiniciará.
     Unknown: no se pudo obtener el estado, normalmente por un problema de comunicación con el nodo.

 kubectl get pods muestra una columna STATUS: CrashLoopBackOff y Terminating no son fases del
 Pod.

 Lifecycle handlers
 postStart puede ejecutarse junto con el ENTRYPOINT. El período de gracia comienza antes de preStop e
 incluye el hook y el apagado del proceso.

   apiVersion: v1
   kind: Pod
   metadata:
     name: lifecycle-demo
   spec:
     terminationGracePeriodSeconds: 30
     containers:
     - name: web
       image: nginx:1.30.5
       lifecycle:
         postStart:
           exec:
             command: ["/bin/sh", "-c", "echo iniciado > /tmp/post-start"]
         preStop:
           exec:
             command: ["/bin/sh", "-c", "sleep 5"]

 Deployment
 Un Deployment proporciona actualizaciones declarativas para Pods y ReplicaSets. Su controlador acerca el
 estado observado al deseado.
 Permite reemplazar progresivamente una versión de la aplicación por otra.
 Un rollout se dispara cuando cambia .spec.template, por ejemplo, la imagen del contenedor. Cambiar sólo
 .spec.replicas escala la aplicación sin iniciar un rollout.

 ReplicaSet
 Mantiene la cantidad deseada de Pods: crea los que
 faltan y elimina los que sobran.
 Identifica sus Pods mediante un selector de etiquetas y
 las referencias de ownership.
 Puede adoptar un Pod ajeno al template si coincide
 con el selector y no tiene otro controlador propietario.

===== PAGINA 37 =====

 Job
 Un Job ejecuta una tarea hasta alcanzar la cantidad prevista de finalizaciones exitosas.
     .spec.completions: cantidad de Pods que deben terminar con éxito.
     .spec.parallelism: cantidad de Pods que se solicita ejecutar en paralelo.

 Por ejemplo: completions: 6 y parallelism: 2 solicitan seis finalizaciones, normalmente con hasta dos
 Pods activos a la vez.
 Los reintentos están limitados por .spec.backoffLimit; .spec.activeDeadlineSeconds permite limitar
 el tiempo total.




                                                                                            Fuente: Kubernetes · Jobs

Microservicios (73.40)                                                                                            37

===== PAGINA 38 =====

 CronJob
 Un CronJob crea Jobs según una programación con sintaxis cron.
     .spec.schedule: cuándo ejecutar; .spec.timeZone: zona horaria, por ejemplo Etc/UTC.
     .spec.concurrencyPolicy: permite ejecuciones simultáneas (Allow), evita solaparlas (Forbid) o
     reemplaza la anterior (Replace) para ese CronJob.

 La programación es aproximada: puede haber ejecuciones duplicadas u omitidas. La tarea debe ser idempotente:
 repetirla no debe duplicar sus efectos.




                                                                                            Fuente: Kubernetes · CronJobs

===== PAGINA 42 =====

 Proceso de reconciliación
 1. El controlador observa recursos a través de la API.
 2. Compara lo observado con el estado deseado.
 3. Solicita acciones mediante la API: crear, actualizar o eliminar recursos.
 4. Otros componentes realizan su parte y reportan lo observado.
 5. El ciclo se repite; los resultados no son instantáneos.

 Cambiar un ConfigMap no inicia por sí solo un rollout del Deployment: para ello debe cambiar el template del
 Pod.




                                                                                    Fuente: Kubernetes · actualización de ConfigMaps

===== PAGINA 48 =====

 Consistencia eventual
 Al crear un Namespace, el plano de control también asegura que exista un ServiceAccount llamado default.
 Estas acciones no forman una única operación instantánea: el ServiceAccount puede aparecer después de que la
 creación del Namespace haya terminado.

   kubectl create namespace fede-ns
   kubectl get serviceaccounts -n fede-ns --watch
   # Luego aparece el ServiceAccount default.

 Consistencia eventual
 1. kubectl solicita crear el Namespace al API server, que lo persiste en etcd.
 2. El serviceaccount-controller observa el Namespace activo.
 3. Si falta default, solicita crear ese ServiceAccount mediante la API.
 4. La API lo persiste y las consultas posteriores pueden observarlo.

 El estado del clúster converge mediante acciones asíncronas. Este intervalo no significa que etcd sea una base de
 datos inconsistente.

===== PAGINA 53 =====

 Service Accounts
     Un ServiceAccount identifica a una aplicación para autenticarse ante la API; los permisos se autorizan por
     separado.
     Con RBAC, Role y RoleBinding conceden los permisos mínimos necesarios.
     Un Pod sin cuenta explícita usa default de su namespace, creada por un controlador.
     Por defecto, los Pods reciben tokens de corta duración, proyectados en un volumen y renovados
     automáticamente.

   kubectl get serviceaccounts -o wide
   # NAME      SECRETS   AGE
   # default   0         27h

 SECRETS 0 es normal: desde 1.24 no se crean automáticamente Secrets con tokens permanentes.

===== PAGINA 54 =====

 Admission Controllers
 Después de autenticar y autorizar una solicitud, la admisión puede modificarla o rechazarla antes de persistir el
 objeto.
     Mutante: modifica el objeto; por ejemplo, un webhook puede inyectar un sidecar.
     Validante: comprueba reglas y puede rechazar el objeto, sin modificarlo.
     Hay controladores integrados en el API server y extensiones mediante webhooks; también se pueden definir
     políticas declarativas.

 Se aplican a creación, modificación, eliminación y ciertas conexiones; get, list y watch no pasan por admisión.

===== PAGINA 55 =====

 Manifiestos
 Un manifiesto YAML o JSON describe un recurso. apiVersion indica la versión de su API y kind, el tipo de
 objeto; no son la versión del clúster.

   apiVersion: v1
   kind: Pod
   metadata:
     name: nginx
   spec:
     containers:
     - name: nginx
       image: nginx:1.30.5
       ports:
       - containerPort: 80

 v1 para Pods y apps/v1 para Deployments siguen vigentes.

===== PAGINA 56 =====

 Namespaces
 Un namespace organiza recursos y define un ámbito para sus nombres. No impone aislamiento de seguridad ni
 de red por sí solo.
     Pods, Services y PersistentVolumeClaims (PVC) pertenecen a un namespace.
     Nodes y PersistentVolumes (PV) tienen alcance de clúster.

   kubectl get namespaces
   # NAME              STATUS   AGE
   # default           Active   30m
   # kube-node-lease   Active   30m
   # kube-public       Active   30m
   # kube-system       Active   30m

 Estos son los cuatro namespaces iniciales; otros dependen de las aplicaciones y componentes instalados.
