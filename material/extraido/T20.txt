===== PAGINA 3 =====

 ¿Qué es GitOps?
     Un modelo de operación para sistemas declarativos.
         El estado deseado se expresa en archivos versionados.
         Un agente lo obtiene de forma automática.
         Un reconciliador hace converger el estado real.

     Los cuatro principios de OpenGitOps:
         Declarativo
         Versionado e inmutable
         Pulled automatically
         Continuously reconciled

 Cambio de paradigma
     No se “ejecutan pasos” como unidad principal de operación.
     Se declara un estado objetivo: el sistema de reconciliación observa la realidad y corrige la divergencia.
     Este cambio parece menor, pero modifica:
         Seguridad
         Auditoría
         Rollback
         Propiedad del cambio
         Respuesta a incidentes

===== PAGINA 7 =====

 Declarativo: trade-offs
     Estado deseado auditable y reproducible.
         Costo: los pasos intermedios quedan menos explícitos.
         Criterio: hooks, sync waves o Jobs cuando haya orden operacional estricto.

     Facilita rollback mediante revert del estado deseado.
         Costo: no siempre revierte datos, migraciones o efectos externos.
         Criterio: separar rollback de aplicación, de datos y de tráfico.

     Reduce scripts ad-hoc.
         Costo: puede ocultar operaciones destructivas detrás de un YAML inocente.
         Criterio: revisión de PR y policy-as-code para cambios sensibles.

===== PAGINA 8 =====

 Versionado e inmutabilidad
     Git funciona como registro de decisiones. Cada cambio debería responder:
         Quién lo propuso y quién lo aprobó.
         Qué se modificó y cuándo se aplicó.
         Cómo volver a una versión previa.

     Pero Git sólo versiona lo que está efectivamente declarado.
     Si el registry permite sobrescribir tags, Git puede decir lo mismo mientras el artefacto real cambió.

===== PAGINA 9 =====

 Tags mutables vs digest
     Tag mutable: cómodo para humanos, riesgoso para auditoría.
         “v1.4.2” puede apuntar a otra imagen si el registry lo permite.

     Digest: más incómodo de leer, pero identifica el artefacto exacto.
         En producción es la opción sólida.

     SemVer + digest: compromiso práctico.
         Semántica humana más reproducibilidad de máquina.

===== PAGINA 10 =====

 Pull-based vs Push-based
     El contraste no es meramente de implementación: cambia el modelo de seguridad y de red.
     Push-based: el sistema CI entra al clúster y aplica cambios.
     Pull-based: un agente dentro del clúster sale a buscar el estado deseado y lo reconcilia.

===== PAGINA 12 =====

 Reconciliación: el loop de GitOps
     Es una extensión del loop de Kubernetes:
     1. Leer estado deseado.
     2. Leer estado real.
     3. Comparar.
     4. Aplicar la diferencia.
     5. Reportar y repetir.

     Drift = divergencia entre lo declarado y lo observado.
     No todo drift es igual: puede ser peligroso, esperado o producido por otro controlador.

===== PAGINA 13 =====

 Fuentes de drift
     Cambio manual — kubectl edit en producción.
         Debe quedar auditado y luego volver a Git o ser revertido.

     Controlador legítimo — HPA cambia replicas.
         No debe pelearse con GitOps: ignorar campos o delegar propiedad.
     Webhook / mutación — service mesh inyecta sidecar.
         Diferencia esperada si está gobernada por la plataforma.
     Defaulting de Kubernetes — campos completados por el API Server.
         No necesariamente es un problema.
     Secreto externo — External Secrets rota un Secret.
         Git no debería contener el valor secreto; sí la intención de consumirlo.

===== PAGINA 14 =====

 Antipatrones de GitOps
     Git como basurero de YAML: manifiestos sin propiedad, revisión ni contrato de promoción.
     GitOps sin inmutabilidad: tags mutables creyendo que el commit alcanza para reproducibilidad.
     Self-heal sin política de incidentes: el controlador revierte cambios manuales necesarios durante
     emergencias.
     Secretos en claro: confundir versionado con exposición de datos sensibles.
     CI con poder total y GitOps decorativo: kubeconfigs en CI y ArgoCD instalado sólo para mirar
     dashboards.

===== PAGINA 16 =====

 ArgoCD: control plane GitOps orientado a aplicaciones
     Modela el despliegue mediante el recurso Application:
         Una fuente declarativa (repo, revisión, path).
         Un destino Kubernetes (clúster, namespace).

     Internamente separa responsabilidades en componentes:
         API server, repo-server, application-controller, Redis, SSO/Dex, notificaciones, ApplicationSet Controller.

 El recurso Application

  kind: Application
  metadata:
    name: payments-api
    namespace: argocd
  spec:
    source:
      repoURL: https://git.example.com/platform/manifests
      targetRevision: main
      path: apps/payments-api/overlays/prod
    destination:
      server: https://kubernetes.default.svc
      namespace: payments
    syncPolicy:
      automated:
        prune: true
        selfHeal: true

===== PAGINA 19 =====

 Arquitectura de ArgoCD (2/2)
     application-controller
         Compara desired state vs live state y ejecuta la reconciliación.
         Riesgo: corazón del sistema. Una mala configuración produce syncs peligrosos o lentos.

     Redis
         Caché para reducir llamadas al API Server y a proveedores Git.
         Riesgo: no es fuente de verdad, pero afecta performance y experiencia.

     ApplicationSet Controller
         Genera Applications a escala para muchos clusters o namespaces.
         Riesgo: muy potente; multiplica errores si el template o generator está mal.

===== PAGINA 20 =====

 Arquitectura
     ArgoCD no es “un pod que hace pull de Git”.
     Es un control plane de entrega continua.
     Si cae:
         Las aplicaciones existentes siguen corriendo.
         Se pierde sincronización, visibilidad, drift detection y operación declarativa.

===== PAGINA 23 =====

 Flux: toolkit de controladores Kubernetes
     Una CLI más una serie de controladores Kubernetes.
     El GitOps Toolkit separa responsabilidades en controladores independientes.
     Diseño más granular y nativo de Kubernetes:
         Cada pieza es un controlador que reconcilia CRDs.
         Más natural para equipos platform maduros.

===== PAGINA 24 =====

 Controladores del GitOps Toolkit
     source-controller
         Obtiene fuentes desde Git, Helm repositories u OCI y produce artefactos.

     kustomize-controller
         Reconcilia Kustomizations y aplica manifiestos ensamblados con Kustomize.
     helm-controller
         Gestiona HelmRelease como recurso declarativo: Helm operado como reconciliador, no como comando
         manual.
     notification-controller
         Emite eventos e integra webhooks: la operación se vuelve observable.
     image reflector / automation
         Detecta nuevas imágenes y propone cambios declarativos. Requiere gobierno para no automatizar
         promociones inseguras.
