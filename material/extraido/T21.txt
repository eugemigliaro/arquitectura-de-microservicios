===== PAGINA 2 =====

 Caso motivador: una falla chica que tumba todo
 Los grandes incidentes rara vez empiezan con una falla grande.
     Un componente interno se degrada (red, DB, dependencia).
     Los clientes reintentan de inmediato y en masa.
     La carga extra satura aún más el componente degradado.
     La falla se propaga a servicios que no tenían relación directa.
     Recuperar requiere frenar el tráfico, no solo arreglar la causa.

 Ejemplos: AWS us-east-1 (dic. 2021), Cloudflare (jul. 2019), Facebook (oct. 2021).

    Pregunta: ¿qué mecanismo habría contenido el daño en cada caso?

===== PAGINA 7 =====

 SLI, SLO, SLA y error budget
    Término              Qué es                             Ejemplo

    SLI                  Métrica medida                     % de requests con 2xx en menos de 300 ms

    SLO                  Objetivo interno                   99.9% en 30 días

    SLA                  Compromiso contractual             Crédito si baja de 99.5%

    Error budget         100% − SLO                         43 min/mes de falla permitida

     Si el budget se agota, se frenan features y se prioriza confiabilidad.
     El SLO decide cuánta resiliencia vale la pena construir.

===== PAGINA 11 =====

 Retries con backoff exponencial y jitter
  def delay(attempt, base=0.1, cap=10.0):
      # full jitter
      return random.uniform(0, min(cap, base * 2 ** attempt))

     Backoff: espaciar los intentos.
     Jitter: desincronizar clientes (evita thundering herd).
     Retry budget: máximo ~10% de requests adicionales.
     Reintentar solo errores transitorios (503, timeouts), nunca 4xx.
     Solo en un nivel de la cadena.

===== PAGINA 12 =====

 Ejemplo: retries en Kubernetes Jobs
  apiVersion: batch/v1
  kind: Job
  metadata:
    name: sync-facturas
  spec:
    backoffLimit: 4                 # reintentos antes de marcar Failed
    activeDeadlineSeconds: 600      # tope total, corta cualquier retry
    ttlSecondsAfterFinished: 3600
    template:
      spec:
        restartPolicy: OnFailure    # Never | OnFailure (Always no vale)
        containers:
          - name: sync
            image: registry/sync-facturas:1.4.2

     Cada falla del pod cuenta contra backoffLimit (default 6).
     Kubernetes aplica backoff exponencial: 10 s, 20 s, 40 s… con tope de 6 min. No es configurable y no
     lleva jitter.

===== PAGINA 18 =====

 Rate limiting y load shedding
 Proteger al servicio rechazando trabajo temprano y barato.
     Token bucket: permite ráfagas, limita el promedio.
     Leaky bucket: salida a ritmo constante.
     Responder 429 Too Many Requests (límite por cliente) o 503 + Retry-After (sobrecarga).
     Load shedding: descartar primero lo menos crítico (prioridades).

    Rechazar el 10% de los requests a tiempo es mejor que fallar el 100% por saturación.

===== PAGINA 19 =====

 Ataques de volumen (DDoS)
 Objetivo del atacante: agotar ancho de banda o recursos hasta que los usuarios legítimos no puedan usar
 el servicio.

    Capa                     Ejemplo                                            Qué satura

    L3/L4 (red/transporte)   UDP flood, SYN flood, amplificación (DNS, NTP)     Ancho de banda, tabla de conexiones

    L7 (aplicación)          HTTP flood, requests costosos (búsquedas, login)   CPU, threads, DB


     Un ataque L7 parece tráfico legítimo: pocos requests bastan si cada uno es caro.
     El autoscaling no es una defensa: escala el costo junto con el ataque (denial of wallet).
     Absorber el volumen es un problema del borde, no del cluster.

===== PAGINA 21 =====

 Mitigar ataques de volumen en Kubernetes
     No exponer NodePorts ni LoadBalancers directos: todo el tráfico entra por CDN / WAF.
     Ingress: limit-rps y limit-connections (ingress-nginx), RateLimitPolicy (Gateway API / Envoy).
     Timeouts de cabecera y body cortos contra ataques lentos (slowloris).
     NetworkPolicy y cuentas de servicio: limitar el movimiento lateral si algo se filtra.
     Capar maxReplicas del HPA y fijar presupuesto: evita facturas y cascadas hacia la DB.
     Cachear en el CDN las respuestas costosas y proteger endpoints caros (login, búsqueda).
     Plan de respuesta: alertas por tráfico anómalo, runbook de bloqueo y contacto con el proveedor.

    Defensa en profundidad: ningún componente solo absorbe un ataque volumétrico.

===== PAGINA 22 =====

 Backpressure
 Que el consumidor lento pueda frenar al productor.
     Colas acotadas: cuando se llenan, se rechaza o se bloquea.
     Flow control: HTTP/2 y gRPC, Reactive Streams.
     Kafka: el consumidor controla su ritmo con poll y max.poll.records.
     Una cola sin límite solo traslada el problema a la memoria (OOMKilled).

===== PAGINA 25 =====

 Qué da Kubernetes "gratis"
 El reconciliation loop mantiene el estado deseado.
     Reinicia contenedores que mueren (restartPolicy).
     Reprograma Pods si cae un nodo.
     Mantiene el número de réplicas.
     Saca del Service a los Pods que no están Ready.

 Lo que NO da:
     Timeouts, retries ni circuit breakers en tu código.
     Idempotencia ni manejo de datos duplicados.
     Capacidad ante la caída de una zona o región.

 HPA: Horizontal Pod Autoscaler
  réplicas = ceil( réplicas_actuales × métrica_actual / métrica_objetivo )

  spec:
    minReplicas: 3
    maxReplicas: 30
    behavior:
      scaleDown:
        stabilizationWindowSeconds: 300

     Ejemplo: 4 réplicas al 90% de CPU con objetivo 60%          ⇒ 6 réplicas.
     behavior evita oscilaciones (flapping): subir rápido, bajar lento.
     Requiere requests de CPU definidos.

===== PAGINA 38 =====

 Cuellos de botella aguas abajo
 Escalar un servicio puede mover el problema a la base de datos.
     50 réplicas × 20 conexiones = 1000 conexiones a la DB.
     Usar connection pooling (PgBouncer, pools acotados).
     Limitar el máximo de réplicas según la capacidad de la DB.
     Rate limit y colas delante de recursos no elásticos.

    Escalar es una decisión de toda la cadena, no de un solo servicio.

 Escalado asincrónico
 Absorber los picos en lugar de resistirlos.
     Queue-based load leveling: la cola amortigua; los workers procesan a ritmo sostenible.
     Competing consumers: varios workers sobre la misma cola.
     Dead Letter Queue: mensajes que fallan N veces se apartan para análisis.
     Combinar con KEDA: escalar workers según el lag.

  API → Cola/Topic → Workers (autoscaling) → DB

 Failover y failback
     Detección: health checks y señales de varias fuentes.
     Automático vs. manual: un failover erróneo puede ser peor que la falla.
     Split-brain: dos regiones creen ser la principal y aceptan escrituras.
     Región pasiva caliente: capacidad reservada, no a cero.
     La región sobreviviente recibe 2× la carga: dimensionar para eso.
     Failback planificado: resincronizar datos antes de volver.
     Runbooks ensayados en game days.

 RTO, RPO y estrategias de DR

     Velero respalda recursos y volúmenes de Kubernetes.
     Un backup no probado no es un backup.

 Observabilidad para resiliencia
 No se puede mejorar lo que no se mide.

===== PAGINA 50 =====

 Chaos engineering
 Provocar fallas controladas para descubrir debilidades antes que los usuarios.
 1. Definir el estado estable (p. ej. checkout con SLO cumplido).
 2. Formular una hipótesis ("si cae un nodo, no hay errores visibles").
 3. Inyectar la falla con blast radius acotado.
 4. Observar, aprender y corregir.

     Herramientas: Chaos Mesh, Litmus.
     Game day: simular la caída de una región con el equipo completo.
