===== PAGINA 11 =====

 Wide Events: el beneficio real
 Narrow logs: reconstruir requiere joins entre servicios
 Wide events:
     Un evento por operación → sin joins
     Todo el contexto disponible → filtrable por cualquier dimensión
     tenant, user_type, feature_flag → siempre presentes
     Debugging sin reproducir el problema
     En OpenTelemetry, los atributos de un span son un wide event

 "Está lento para usuarios premium en mobile" → un filtro sobre los campos, no horas cruzando logs.

===== PAGINA 12 =====

 Métricas
 Medición numérica que se agrega en el tiempo: no
 guarda cada request, guarda contadores.
     Counter: solo sube (requests, errores). Se mira su
     ritmo con rate().
     Gauge: sube y baja (memoria, conexiones abiertas,
     mensajes en cola).
     Histogram: cuenta valores por rangos (latencia). De
     ahí salen los percentiles.
                                                           Nombre + labels identifican la serie.
                                                           Cada muestra es timestamp + valor.

===== PAGINA 13 =====

 Cardinalidad: cuidado con los labels
 Cada combinación de valores de labels es una serie nueva en Prometheus.

   http_requests_total{service="orders", status="500"}     # decenas de series
   http_requests_total{service="orders", userId="u-456"}   # una serie por usuario

     Labels con pocos valores posibles: servicio, endpoint, status, región
     userId, orderId, traceId → millones de series: Prometheus se queda sin memoria
     Ese detalle va en el wide event o en la traza, no en la métrica
     Por eso conviven: la métrica es barata y agregada; el evento tiene todo el detalle

===== PAGINA 20 =====

 Tracing distribuido
 El tracing se refiere a la capacidad de rastrear una solicitud a través de múltiples servicios.
     Trace: vista de end-to-end de una solicitud a medida que pasa por varios servicios.
     Span: unidad individual de trabajo realizada dentro de un solo servicio
     Múltiples spans forman parte de un trace.
     Spans tienen parent → Árbol causal de la request

===== PAGINA 22 =====

 Propagación del Contexto
 Cada servicio recibe y envía el Trace ID en header HTTP:




   traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
                │ └──────────── trace-id ────────┘ └─ parent-id ──┘ └ flags
                └ versión

     Estándar W3C Trace Context (W3C Recommendation, 2020)
     En colas y Kafka viaja igual, en los headers del mensaje
     Un servicio sin instrumentar corta la traza
     El SDK lee el header al recibir y lo escribe al llamar: el código de negocio no se entera

===== PAGINA 25 =====

 OTel: Auto vs Manual instrumentation
 Auto-instrumentation (cero cambios en código):

   # Java — el agente intercepta HTTP, JDBC, Kafka automáticamente
   java -javaagent:opentelemetry-javaagent.jar -jar app.jar

 Manual instrumentation (contexto de negocio):

   with tracer.start_as_current_span("process-order") as span:
       span.set_attribute("order.id", order_id)
       span.set_attribute("order.amount", amount)
       span.set_attribute("user.tier", "premium")

 Auto da la estructura; manual agrega el contexto de negocio. Lo ideal: combinar las dos.

===== PAGINA 34 =====

 traceId vs correlationId
 traceId                       correlationid
     Una ejecución técnica       Una operación de negocio: el intercambio
     Nace con el request         Vive días, sobrevive reintentos
     Viaja en traceparent        Viaja en el CloudEvent (extensión)
     Lo genera OpenTelemetry     Lo genera tu dominio

                               ¿Y si la compensación la dispara un vencimiento?
                               Un job no tiene request de origen: arranca otra traza. Se une
                                por el correlationid como atributo del span, o con un
                                       span link (un span que apunta a otra traza).
